# ADR 005: TTS backends and burst playback into Twilio

## Context
Prompts must be spoken on the call (language selection + DTMF menu). Windows SAPI is available for local smoke; production needs a path to Piper. Early realtime ~20 ms frame pacing sounded choppy on live calls because WebSocket/event-loop jitter inserted gaps.

## Decision
- TTS protocol in `services/ivr/tts.py`: prefer Piper when configured; else Windows SAPI; else tone stub.
- Cache synthesized μ-law under `.cache/ivr-tts/` and warm common prompts at app startup.
- Default `IVR_PLAYBACK_REALTIME=false`: burst enqueue (or a single payload) into Twilio’s buffer so playback stays smooth. Optional realtime pacing remains for experiments.
- On barge-in / digit: stop local enqueue and send Twilio Media Stream `clear` so buffered menu audio stops immediately.

## Trade-off Analysis
- **Benefit:** Smooth prompts on live Twilio; cold SAPI latency amortized by cache/warmup; barge-in can cut the menu.
- **Drawback:** Burst mode means “play done” in-process is not the same as “caller finished hearing”; listen windows must account for audio duration. SAPI remains too slow/accented for production multilingual TTS.
