# ADR 019: Local grammar STT for placeholder tasks

## Context
Phases 4–7 use `ScriptedStreamingSpeechToText`, which ignores the caller’s audio. Live demos needed `IVR_STT_SCRIPT` so “balance” played after a pause. The original feature asked for streaming STT (Deepgram or a local equivalent) behind the same protocol. A paid streaming vendor would keep TTFB closer to 500 ms; this slice must stay **free and local**.

Windows already hosts SAPI. Dictation is slow and messy. The IVR only needs a handful of placeholder commands.

## Decision
- Add `GrammarStreamingSpeechToText` (`services/ivr/sapi_stt.py`) implementing `StreamingSpeechToText`: buffer μ-law → on `finish()`, recognize against a **small grammar** (English or French command list from `grammar_phrases`).
- Select with `IVR_STT_BACKEND=sapi`. The scripted stub remains the default (`scripted`) for CI and Phase 7. `IVR_STT_SCRIPT` is ignored while `sapi` is selected.
- CI default remains `scripted`. Tests inject a fake `recognize` function; they do not call PowerShell.
- Do not write call audio to a lasting cache. Temp WAVs are deleted with the process temp dir.
- **TTFB still starts at `speech_end`.** Grammar recognition runs on that clock, so live TTFB will often exceed 500 ms. Log `grammar_stt … stt_ms=`. A later Deepgram (or similar) streaming backend is the path back to the canned SLO with real speech.
- Cloud / Whisper-class engines keep the same constructor swap (ADR-014).

## Trade-off Analysis
- **Benefit:** On a handset, saying “balance” can play the fake-balance line with no paid API and no script queue. Tests stay offline.
- **Drawback:** Not true streaming STT; SAPI file recognition is batch and Windows-only; other languages need an installed recognizer culture; 500 ms canned SLO is for the scripted/warmed path until a streaming vendor is plugged in.
