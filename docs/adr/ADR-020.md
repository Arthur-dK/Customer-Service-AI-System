# ADR 020: Stub caller/card SQLite + gitignore overlay

## Context
FEAT-04 uses the inbound phone number as the primary security check and needs fake card fields (last-4, balance, blocked, statement) for spoken replies. The same stub records will later be used by SMS and Email. Real numbers and PINs must not land in git. Render has no operator laptop file.

## Decision
- Keep channel code in `services/ivr`, `services/sms`, and `services/email` only. Shared card/caller data lives in `core/cards/` so no channel owns the store.
- Canonical lookup key is E.164 via existing `phonenumbers` parsing (same family as `resolve_caller_locale`). Empty, `anonymous`, `restricted`, and unparseable values are misses.
- Load committed `data/callers.example.json` (reserved test numbers only, **no PIN field**), then merge gitignored `data/callers.local.json` and/or env `CALLER_OVERRIDE_JSON`.
- Persist a process-local SQLite file (`data/callers.sqlite`, gitignored) so later phases can update `blocked` for the rest of the process.
- One card may have many phones. PIN is overlay-only and never returned as digits on the public `StubCard` (only a `has_pin` flag).
- Logs use `last4_phone` (last four *digits* of the number), never the full E.164.

## Trade-off Analysis
- **Benefit:** IVR, SMS, and Email can import the same store; operators can demo with their own number without committing PII; CI uses only example JSON.
- **Drawback:** Render disk is ephemeral; sqlite is rebuilt from JSON+secret on boot, so block state does not survive deploys.
