# ADR 011: TTFB clock for IVR reply audio

## Context
Voice replies must feel instant. Language selection already records `time_to_first_speech_ms` (when the *caller* starts talking). We need a separate clock for *our* reply: after the caller stops, how long until we start sending audio back.

## Decision
- **Start:** energy VAD `speech_end` — the caller's voice energy has dropped for the hangover window (`speech_end_ms` in `VadConfig`). Same marker as today's utterance boundary.
- **Stop:** first reply μ-law bytes are handed to the outbound Media Stream sender (enqueue). Not Twilio/handset delay.
- **Canned / templated prompts** (menus, errors, placeholder tasks): typical (median) TTFB ≤ **500 ms**.
- **Future LLM sentences:** typical TTFB ≤ **5000 ms**. No LLM on this feature's hot path.
- Implement a reusable `TtfbHarness` (`services/ivr/ttfb.py`) with an injectable clock for tests. Wire it into the turn engine in later phases.

## Trade-off Analysis
- **Benefit:** Automated tests can assert the 0.5s goal without a live phone; definition stays stable when STT/TTS backends swap.
- **Drawback:** Passing TTFB in-process can still sound slower on a real call (network + Twilio buffer). Live smoke remains a second check, not the official CI clock.
