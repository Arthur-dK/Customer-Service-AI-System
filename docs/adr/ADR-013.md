# ADR 013: Streaming TTS protocol (chunked μ-law)

## Context
TTFB stops when the first reply audio is sent. Batch TTS (SAPI, Piper CLI, tone) produces a whole utterance before any bytes exist. Cloud streaming TTS can emit audio before the sentence is finished. Callers should not care which engine is used.

## Decision
- Add `StreamingTextToSpeech` in `services/ivr/streaming_tts.py`: async iterator of 8 kHz μ-law chunks (default 20 ms).
- **Free stub:** `ToneStreamingTextToSpeech` (no paid API).
- **Swap path:** `BatchStreamingTextToSpeech` wraps today’s `TextToSpeech`. Native streaming vendors (e.g. Cartesia) implement the same protocol later.
- **Canned lines:** `stream_ready_phrase` chunks `PhraseAudioCache.get_ready` so the first frame does not wait on TTS.
- `enqueue_tts_stream` writes base64 frames to the outbound queue and calls `TtfbHarness.mark_first_audio_byte` on the first non-empty chunk.
- Live Twilio may still *burst* concatenated frames (ADR-005) in a later wiring phase; the stream interface still defines first-byte TTFB.

## Trade-off Analysis
- **Benefit:** Tests and the turn engine depend on one interface; paid/private engines plug in by constructor. Phrase playback stays inside the 500 ms canned budget.
- **Drawback:** Wrapping batch TTS does not reduce synth latency — only native streaming (or ready phrase buffers) can emit the first chunk before the full utterance exists. Barge-in still needs `cancel` plus Twilio `clear`.
