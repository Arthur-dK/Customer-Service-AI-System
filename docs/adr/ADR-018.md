# ADR 018: Match TTS voice to call language

## Context
Language ID can select French (or any VoxLingua/LLM language). Catalog text is already translated. Windows SAPI (and a single English Piper model) still synthesized that text with an **English** voice, so French was unintelligible. `supports_language` was used only to skip warmup, not to block `synthesize`.

The product needs **any** language the future LLM can use, not a hard-coded English+French pair. Shipping 50 local models in this branch is unrealistic; the call path must still refuse the wrong voice.

## Decision
- **Never** synthesize language L with a voice tagged for another language.
- **Windows SAPI:** list installed voices and `SelectVoice` by culture. Extra Windows speech packs become new languages with no code change.
- **Piper:** one `.onnx` file speaks one language (filename `fr_FR-…` or `IVR_PIPER_VOICES` JSON / `IVR_PIPER_VOICE_DIR`). `RoutedTextToSpeech` picks the first backend that `supports_language`.
- **Phrase cache:** if there is no voice for the catalog language, play **English audio of English text**, not English-accented foreign text.
- **Later cloud TTS** (Azure, Google, Cartesia, …) implements the same `TextToSpeech` protocol and passes `language` to the vendor — that is how dozens of LLM languages get voices without a local model each.
- Delete stale `.cache/ivr-phrases/*.fr.mulaw` (and similar) after this change if they were rendered with the wrong voice.

## Trade-off Analysis
- **Benefit:** Callers are not asked to decode English-pronounced French. Adding a language is “install or point at a voice,” not a rewrite of the turn engine.
- **Drawback:** Until a French (etc.) voice exists, the IVR speaks English after a French LID result. That is degraded but intelligible. A paid multilingual API is still a constructor swap, not a new pipeline.
